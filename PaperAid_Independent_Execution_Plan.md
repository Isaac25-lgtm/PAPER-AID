# PaperAid: independent execution plan

**Prepared:** 23 September 2026  
**Purpose:** A practical plan to compare with the two PaperAid handoff files.  
**Planning assumption:** One strong full-stack engineer, with part-time product/design review and access to a second reviewer for security and document quality. Calendar estimates change substantially if those people are unavailable.

## 1. What I understand the product to be

PaperAid sells completed academic-document jobs. A student or researcher supplies a paper, chooses a clearly defined service, sees an authoritative quote, and later receives a report or downloadable result. It is a service desk for documents, not a general chat assistant or a live collaborative editor. The service catalogue consists of AI Check, Check + Refine, Academic Formatting, University Template Formatting, Deep Redraft, and LaTeX Conversion. A combined service can be offered once its component pipelines are reliable. An uploaded university guide has a distinct role from the paper being processed.

The handoff fixes the broad architecture: React, TypeScript and Vite in the browser; Firebase Hosting, Authentication, Firestore, Storage and App Check; a Python FastAPI application on Cloud Run; Cloud Tasks for asynchronous processing; and server-side model integrations with OpenAI and Anthropic. It also fixes important product principles: show a polished interface early at `localhost:5000`; keep payments disabled while proving the core journey; treat DOCX as the best editable input; reject scanned PDFs in the first release; preserve citations, numbers, facts and untouched text; avoid a sprawling codebase; and keep security, cost and recovery visible. My plan works inside those boundaries.

I see the largest risk as trust, rather than raw implementation speed. A good-looking app can still damage a dissertation, overstate an AI detection claim, quote one file and process another, charge for a failed job, or release a document to the wrong account. I would organize the work around proving that each promised outcome is safe and understandable. The interface will arrive first, as requested, but the public service catalogue will be turned on one capability at a time using explicit release gates.

## 2. The decisions I would make before writing application code

First, I would write a one-page product contract that says exactly what each service does to each input format. The handoff correctly favors DOCX but leaves a few customer-facing edge cases to settle. My initial matrix would allow AI Check for valid DOCX and text-based PDF; Check + Refine for both, while telling PDF users that the editable result is a newly generated DOCX with potentially different layout; Academic Formatting and University Template Formatting for DOCX only; Deep Redraft for DOCX, with PDF support added only if reconstruction quality is proven; and LaTeX Conversion for DOCX only at first. The user would see compatibility before buying. The backend would enforce the same matrix. A service would never appear selectable merely because its card exists on the landing page.

Second, I would define what the phrase *Estimated AI-likeness* is allowed to mean. An internal model can identify passages with repetitive, generic or formulaic language, but a precise number may imply a reliability we have not earned. I would retain the specified score architecture, yet make its public display conditional on an evaluation gate. The evaluation set should contain consented or synthetic texts across disciplines, lengths, writing skill levels, quotations, reference-heavy papers and known AI-assisted passages. We should inspect false positives and variation under small edits, not just whether examples look plausible. If the score cannot be interpreted consistently, the first public AI Check should show passage-level writing-pattern findings and uncertainty while the numeric score remains in private evaluation. That is a deliberate point for us to compare: the handoff expects a displayed estimate; I would require evidence before making a number a sales claim.

Third, I would define an academic-integrity policy. The product should present refinement as preserving the student's ideas and improving clarity, organization and format. It should not promise to defeat a detector, certify human authorship, invent citations, fabricate research data or disguise outsourced writing. Deep Redraft deserves especially clear wording and a visible record of how much changed. This is part of product design, prompts, audits, help copy and support practice. It also reduces the chance that the team gradually optimizes for a misleading score instead of document quality.

Fourth, I would lock the privacy defaults before storing real papers. We need a public retention statement, a chosen default period, deletion behavior for source/output/internal artifacts, and a clear explanation that external model providers process relevant text. Thirty days is a reasonable implementation starting point from the handoff, but the actual policy should be reviewed before a public beta. I would include deletion verification in release tests; a button alone is not a deletion workflow.

Fifth, I would make the first beta explicitly payment-free. It should still display a calculated quote or indicative price for research, but the submit action must say that the beta is free and record `BETA_BYPASS`. The landing page must not say “Pay” as though payment works. Price examples in the reference image are design placeholders, not approved commercial prices. We can learn about willingness to pay through interviews and quote acceptance without putting a payment provider on the critical path.

These decisions should be recorded in short decision notes, each with a date, chosen behavior and an owner. I would keep the notes in `docs/decisions/` and revisit them only when evidence changes. This prevents a later implementation detail from silently becoming product policy.

## 3. Success criteria and a realistic release shape

I would call the first public beta successful when a new user can sign in, upload a supported document, receive an inspected quote, submit once, leave the browser, return to a truthful progress page, and download an output or read an actionable failure. The document must remain private to its owner. A support operator must be able to locate the job, understand its stage, cost and failure code, and retry only when safe. Ten simultaneous submissions should queue without duplicate processing or an unusable API. A final output should be automatically checked and sampled visually before the service is advertised as reliable.

I would not wait for all six services to pass before releasing any beta. Instead, I would build one complete vertical path and expand the catalogue. AI Check is a useful first pipeline for proving extraction, findings, reporting and delivery. Academic Formatting is a good second independent path because it validates document preservation without model rewriting. Check + Refine would follow once block mapping, protected spans and audit are solid. University formatting, Deep Redraft and LaTeX should be enabled individually after their own quality gates. The public site can explain future capabilities carefully, but disabled capabilities should not be sold, quoted or shown as working controls. This sequence keeps the handoff's target catalogue while giving us a truthful launch path.

For planning, I would budget roughly twelve to sixteen calendar weeks for a credible payment-disabled beta with one primary engineer. This is an estimate, not a promise. A second experienced engineer and rapid product reviews could shorten it; difficult DOCX cases, provider approvals or infrastructure setup could lengthen it. The first reviewable visual should arrive within the first one to two weeks. A narrow, secure AI Check path should be testable around the middle of the schedule. The final weeks should be reserved for failures discovered in realistic documents and security tests, because those issues rarely respect the planned feature order.

My release gates are: **Visual**, meaning every major route exists at port 5000 and works with fixtures; **Core workflow**, meaning authenticated upload, inspected quote, queue, status and delivery work with a mock provider; **Document integrity**, meaning representative real files survive extraction/export and preservation checks; **Model quality**, meaning paid providers produce validated outputs within budget and failed audits stop delivery; **Operations**, meaning security, deletion, load and runbooks work; and **Public beta**, meaning only services that passed their own acceptance tests are enabled. Each gate produces a short demonstration and a recorded list of remaining defects.

## 4. Stage 0: discovery and technical proof of the dangerous paths

Before building much UI, I would assemble a small, non-sensitive fixture library. It should contain short and long DOCX files, a paper with headings and tables interleaved, references, footnotes, citations, quotations, page sections, a landscape table, a guideline document, text-based PDFs, a scanned PDF, an encrypted PDF, a macro-enabled file and malformed containers. These files should be synthetic or explicitly licensed for testing. Each fixture needs a description of what must survive processing. I would also record expected output characteristics, such as “body wording unchanged” for formatting and “only target paragraph changed” for refinement.

I would run two brief spikes. One checks whether `python-docx` plus targeted OOXML can preserve the high-risk Word features in our fixtures when changing a paragraph and applying styles. The other checks extraction quality and scanned-page detection for PDFs. The goal is to learn where the promised service matrix needs a boundary, not to build the final engine prematurely. A particularly important test is a paragraph with multiple styled runs, hyperlinks, citation fields and tracked changes: naive replacement can flatten structure. The output of the spike should be a compatibility note and a list of files we must reject or handle cautiously.

The third early artifact is a threat and failure map for one paper job: who can read each object, which operations spend money, what happens if an upload is replaced after quoting, where a worker can restart, and where private text could leak into logs. This is a compact engineering note, not a ceremonial security document. It will drive the data model and test plan from the beginning.

## 5. Stage 1: a polished, complete visual product at localhost:5000

I would create a small repository with `web/`, `backend/`, Firebase configuration, scripts and docs. The web app runs on port 5000, with one command in the README. The visual build uses a fixture adapter so screens consume stable job and quote shapes; page components do not contain scattered mock objects. The adapter will later call the real API without redesigning each route. I would use a short set of color, typography, spacing, radius and elevation tokens, and a modest shared component layer for controls actually used by several screens.

The landing page should make the finished-job proposition clear in the first viewport: upload a paper, choose work, receive a checked or improved artifact. I would build the hero preview as responsive HTML/CSS components showing a believable paper excerpt, findings and a concise result summary. That follows the Word file's visual reference while staying original and crisp on mobile. The green accent, white space and restrained cards are useful cues; the exact layout, iconography and copy should be ours. Feature cards must obey service availability flags, so the marketing site cannot advertise a disabled checkout path as ready.

I would then implement the sign-in/register screens, dashboard, new-job form, canonical job page, results variants, history, settings and admin shell. Every route should include realistic empty, loading, invalid, processing, complete, failed and expired states. The new-job screen must make the primary file and optional guideline visibly distinct. The quote section should show what was inspected, what service is selected, what output to expect and when the quote expires. The job page should show named stages, not a decorative percentage that moves independently of actual work. The result page should keep the original available as a separate artifact where policy permits and make warnings as visible as success.

I would test the visual milestone at phone, tablet and desktop widths, plus keyboard-only navigation. One meaningful review should ask a new student to explain what will happen after pressing Submit; another should ask whether a PDF user understands the output limitation. I would fix misunderstandings before connecting the backend, because copy and layout errors become more expensive after state contracts harden. This milestone ends with a live local demonstration, screenshots of the main routes and a short design decision log.

## 6. Stage 2: identity, upload and quote as one secure transaction

The backend starts with Firebase ID-token verification, App Check where required, ownership checks, structured error responses and a small FastAPI API. Users have minimal profile records. Firestore contains safe metadata; Storage contains source files and large artifacts. The browser may upload directly to a constrained Storage path, but the server decides which path belongs to the authenticated user and which file role it represents. Storage rules should prevent users from writing output or privileged internal paths. The server repeats file validation even after a browser-side success message.

My main addition to the handoff is an explicit **draft job** flow. The server creates a stable draft ID and upload slots. The user uploads a source and optional guideline into that draft's job-scoped paths. A finalize/inspect request then verifies the Storage objects, reads their generation identifiers and hashes, validates format and limits, extracts metrics, and records an inspection snapshot. The quote binds to that snapshot: owner, draft ID, source object generation/hash, guideline generation/hash if present, chosen services, metrics, pricing version, currency, amount and expiration. If the file changes or a service is switched, the quote is invalid. Submission uses the draft and accepted quote exactly once. This closes the gap between “server quote” and “process the file the student actually accepted.”

I would keep the API small; the exact route names can follow the handoff's surface, with a draft/upload preparation step if needed. The pricing function takes typed metrics and service options, rounds in one place, and returns a versioned immutable result. The frontend displays the server result verbatim. Even in beta, quote creation should expose useful operational data: selected service, word count band, price band and the reason a service is unavailable. Any quote analytics should avoid storing paper text.

File intake needs more than extension checking. The worker or inspection endpoint should verify MIME and container signature, archive entry count and expansion ratio, size, encryption and macro-enabled formats. It should enforce page and word limits before model calls. A PDF with negligible extractable text must receive a clear “please upload an editable document or text-based PDF” response. Original filenames are display labels only; storage object names are generated. If a user deletes a draft or an inspection fails, orphaned upload objects must be cleaned up by a scheduled, idempotent process.

At the end of this stage, two emulator users should demonstrate strict ownership: one can complete their own draft and cannot read or mutate another's job or Storage path. The test must also prove that the client cannot write quote amount, payment status, progress, admin state or output paths. This is a hard gate; a nice UI cannot compensate for a permissive rule.

## 7. Stage 3: queue, state machine and recoverable mock processing

Next I would make one submitted job flow through Cloud Tasks using a deterministic mock processor. Job and payment states are separate. The transition table lives in one module, so API requests, task handlers and admin actions cannot invent new paths by assigning strings. A real job can progress from uploaded and quoted, through a beta payment bypass, queued, the relevant processing stages and finally completed or a classified failure. Only service-specific stages appear to the user. Stage timestamps and safe messages are persisted so a reopened browser shows the same truth.

Cloud Tasks delivers a job ID to a service-authenticated internal endpoint. The worker acquires a lease or transactional claim on that job, checks its current state, and exits harmlessly for duplicate delivery after completion or while another valid worker owns it. Before calling a provider or writing a final result, it persists the stable stage input and an idempotency key. Major stage artifacts are saved before state advances. On restart, the worker loads the completed artifact and continues. This matters because the model call may cost money, and Cloud Tasks delivery can repeat. We should aim for effectively once-per-stage paid work using persisted call identity and checkpoints, while recognizing that an external provider call and a Firestore write cannot form a true atomic transaction. The remaining crash window should be documented and bounded by spend limits.

The initial queue dispatch target is about five active paper jobs; the backend still accepts ten eligible submissions in a burst and shows the rest as queued. I would configure an active-job cap per user, simple per-user throttles for quote/submit requests and a server-side pause switch. Cancellation is immediate for drafts and queued jobs, but an active model call may finish before cancellation takes effect. The UI should say that plainly. Transient provider or network failures retry within a small policy; invalid files, missing ownership, unsafe output and exhausted budgets finish with a safe final error. Retry attempts never reset the job budget.

This stage's demonstration uses mock providers and a deliberately slow worker. I would submit ten jobs, close the browser, reload job URLs, inject a duplicate task, simulate worker interruption and confirm one output per job, bounded concurrency and a responsive dashboard. That proves the application is truly asynchronous before any paid model integration masks design mistakes.

## 8. Stage 4: the document engine and preservation rules

The internal DocumentModel should be an ordered sequence of stable, typed blocks with IDs, section context and source references. It must distinguish prose, headings, lists, table cells, captions, quotations and references. For DOCX, extraction walks paragraphs and tables in their actual order and remembers the source locations and style/run information needed for safe patching. For PDF, it captures text and page provenance but marks layout fidelity as limited. The model is not a universal publishing format; it is the smallest representation needed to analyze, rewrite selected text and explain the result.

I would implement preservation as two layers. Before rewriting, detect and protect citations, direct quotes, URLs, dates, numerals, equations or other sensitive spans where practical. After rewriting, compare protected values and structured facts with the source. A model can still alter meaning while preserving every numeral, so a separate semantic audit is required later. Unknown block IDs, missing placeholders, duplicated citations and malformed Unicode should fail the candidate revision. The code should patch only accepted blocks into a copy of the original DOCX, leaving unchanged paragraphs and document relationships alone. If a block is too structurally complex to patch safely, the service should warn or reject that file rather than flattening it silently.

Formatting has a different invariant: no body prose rewrite at all. The engine parses a typed FormattingSpec, changes styles and section/page properties deterministically, and compares normalized body text before and after. It should preserve intentional landscape sections and other exceptions, not impose a global style blindly. A formatting-only result must fail automated quality control if content changes outside legitimate fields or generated numbering. Synthetic fixtures should be rendered for visual comparison because a text checksum cannot reveal clipped tables, collapsed headings or a broken title page.

I would build a small document inspection CLI for developers: input file, extracted block list, detected spans, warnings and output comparison. This is an idea beyond the handoff that should pay for itself quickly. Document bugs are hard to diagnose through a browser. A CLI using the same engine makes regression fixtures, support reproduction and visual QA faster without creating another service.

## 9. Stage 5: real AI Check, refinement and measurable quality

The first live provider pipeline should be AI Check because it never modifies the source. The orchestrator sends analyzable blocks with limited outline context, asks for validated findings keyed by known block IDs, and rejects malformed or out-of-scope responses. References, long quotations, code-like areas and table-heavy material receive explicit treatment in the aggregation. The displayed estimate, if released, is computed by versioned server code from block findings, with uncertainty based on text quantity and structure. The report should emphasize passages and reasons, not a single number. Prompts and schema versions are recorded with each artifact so later model changes do not make old results uninterpretable.

Before a public score is shown, I would run the evaluation gate described earlier. This is not an attempt to build a scientific authorship detector in V1. It is a way to check whether the user-facing explanation is stable enough to be honest. We should ask whether similar passages receive similar findings, whether quoted and reference material are handled, whether different disciplines trigger misleading patterns, and whether before/after changes mean what the UI implies. A disclaimer is necessary but does not excuse a number that performs poorly. If the number fails, the passage report can still deliver value while the scoring feature is refined privately.

Standard refinement starts from analysis findings and an explicit intensity. Deterministic thresholds select candidate blocks. The model sees the local section outline, neighbor text and protected placeholders; it does not receive the whole paper repeatedly unless context genuinely requires it. The response is mapped to stable block IDs. Deterministic checks run first, then an independent audit model evaluates meaning drift, invented claims, broken transitions and changed source details. Only failed blocks receive one or two bounded repairs. When the output still fails, the job ends with a quality warning and no “improved” document. That may feel strict, but a failed job is less harmful than a convincing document with invented claims.

Model adapters should be narrow: one for each provider and a deterministic mock. Model IDs, timeouts, prices and task assignments belong in configuration. I would not commit to any particular premium model until a small benchmark on our own fixture tasks compares preservation, quality, latency and cost. Each call records stage, provider, model, prompt version, token usage, duration and estimated cost without storing raw text in operational logs. A pre-call spend guard estimates worst reasonable usage and rejects a stage that would exceed both its job budget and a platform ceiling. Provider retries count toward the same cap. Spend anomalies should be visible in admin before they become a billing surprise.

## 10. Stage 6: formatting guides, deep redraft and LaTeX

University formatting needs a separate guide parser. It extracts text and useful style information from the guideline, then turns explicit rules into a typed FormattingSpec with provenance for each important value. Conflicts should be reported, not arbitrarily resolved. The user sees a short summary such as paper size, margins, font, spacing, heading and numbering rules before accepting the expensive work. The deterministic formatter consumes the frozen spec. Where a guide is vague or contradictory, the output should list assumptions and unresolved items. Curated university presets can later use the same spec, but I would avoid creating a preset library before real user demand identifies common institutions.

Deep Redraft is a separate pipeline and price tier. It needs a section plan, a rough change-scope band, per-section source/output artifacts and a final independent audit. It must not invent study participants, findings, data, methods, citations or sources. I would launch it only after a human review sample demonstrates that the audit catches substantive drift. The output page should summarize which sections changed and how heavily. If a customer expects an entirely new argument, that request is outside the service. Deep Redraft should remain hidden until the stronger evidence threshold is met, even if standard refinement is working well.

LaTeX should be treated as a controlled export, not a place to execute user code. I would generate `.tex` from the internal model or a pinned converter, normalize asset names, preserve plain references if structured bibliography data is unavailable, and optionally compile only in an isolated constrained environment. A `.tex` package may be useful even if PDF compilation fails, but the job result must say so clearly. I would start with representative, uncomplicated papers and hide the service until the result is reliably usable. Complex Word layouts need an upfront limitation message. A compiled PDF should never be promised for every DOCX.

Each additional service gets its own acceptance sheet: supported formats; expected output; preservation invariant; quality fixtures; failure messages; cost band; and customer-facing limitation. This makes release decisions observable. “The code runs” is not enough to put a service on the pricing page.

## 11. Stage 7: operations, security and production hardening

The admin console should answer five questions quickly: what is queued, what is failing, what did each job cost, can a failed job be retried safely, and can we trace an incident by job ID? It should show summary metrics and a paginated job table, but not paper contents by default. Admin authority comes from verified custom claims on the backend. Retry and cancellation actions are state-aware, recorded with actor and time, and idempotent. I would add an emergency processing pause that stops new model work without deleting accepted jobs. Changing that switch should be operationally simple and auditable.

Operational logs should include request ID, job ID, stage, duration and safe error code. They should exclude paper text, full prompts, secrets and signed download links. A small dashboard or alerts should cover API errors, stuck queue, repeated worker failures, unexpected spend and failed cleanup. A readiness endpoint checks configuration without calling a paid provider. The runbook should show how to investigate a queued job, a provider rate limit, corrupt output, cross-user access, key compromise and rollback. I would rehearse at least one failure and one rollback in a non-production environment, rather than treating the runbook as prose only.

Security testing must include Firestore and Storage rules, backend owner checks, task OIDC identity, production App Check, file-container validation, prompt-injection content inside a paper and signed-download expiry or authenticated proxy behavior. I would scan the built web bundle for secrets and verify that development bypasses fail closed in production. The account deletion flow must find all job-scoped objects, including internal artifacts, and report pending cleanup honestly. A scheduled retention worker should be idempotent and retryable. If deletion fails, operators need an alert and a way to resolve it.

CI should run frontend type checking, linting, tests and build; backend type/lint checks and targeted tests; emulator security tests; and a small number of browser journeys. Tests should concentrate on money, confidentiality and document integrity. The highest-value cases are stale quote after file replacement, double submit, duplicate task, worker restart after paid stage, cross-owner access, formatting-only text invariance, lost citation, scanned PDF rejection and budget exhaustion. Visual regression checks are useful for a few key responsive screens, but I would not build an enormous screenshot suite that blocks routine copy edits.

Before public beta I would run ten simultaneous mock-provider submissions and a small controlled real-provider smoke test. I would inspect queue depth, API responsiveness, job latency, usage accounting and failure messages. Production deployment should be scripted and versioned, with documented rollback to prior Cloud Run and Firebase Hosting releases. After deployment, one synthetic end-to-end job should confirm upload, queue, provider or mock path as configured, output and secure download. If it fails, the release remains incomplete even if the deployment command succeeded.

## 12. Payment integration after a stable beta

Payment should begin only when the non-payment service has reliable completion, clear refunds/failure policy, measured per-job costs and a selected provider that fits the target customers. The state model already separates quote, payment and processing. The provider adapter can therefore initiate checkout, receive a verified server-side callback, reconcile amount and currency against the immutable quote, and release the job exactly once. A browser redirect must never mark a job paid. Duplicate callbacks should be harmless by provider transaction ID. I would first test pending, failed, expired, duplicate and delayed payments in a sandbox, then enable a small controlled paid cohort.

The commercial design should account for failed jobs. A customer who has paid but receives `FAILED_FINAL` needs a defined refund or credit path and a visible support explanation. This policy should be written before charging, because payment correctness is more than webhook verification. I would also compare estimated model and infrastructure cost with actual accepted quote by service and document-size band. If a tier has poor margins, adjust pricing or scope transparently rather than weakening citation or safety audits.

## 13. Milestones, ownership and review cadence

I would use a weekly review with a running product demonstration, a short defect list and decisions needed from the owner. Weeks 1–2 cover decisions, fixture corpus and the complete visual app. Weeks 3–4 cover Firebase identity, secure draft upload, inspection and quotes. Weeks 5–6 cover Cloud Tasks, state transitions and mock end-to-end processing. Weeks 7–9 cover DocumentModel, DOCX/PDF extraction, export and formatting preservation. Weeks 10–12 cover real AI Check and refinement with evaluation and audit. Weeks 13–16 cover optional services that pass their gates, admin, security, load, deletion and beta launch. These are planning bands; they should be revised after the early document spikes. A narrow beta may launch earlier with fewer enabled services if every advertised capability is honest and supportable.

The engineer owns implementation, tests, deployment scripts and technical decision notes. The product owner must approve customer-facing promises, service boundaries, retention wording and beta pricing presentation. A design reviewer should evaluate the early visual milestone and mobile flow. A second technical reviewer should examine access rules, deletion and the model-preservation pipeline before public data enters the system. If there is no separate reviewer, I would schedule explicit review time and document the increased risk rather than silently assuming review happened.

At each gate I would bring concrete evidence: a running route, a processed fixture, an emulator deny test, a traceable job, a cost record or a load-test result. The most important comparison with the handoff is this: the handoff describes what the finished system should contain; this plan sets the order in which we prove it can be trusted. My recommended first action after we compare plans is to approve the service/input/output matrix and numeric-score release rule, then build the fixture set and localhost visual milestone. Those choices determine the rest of the implementation more than a folder tree or a model name does.

I would keep one visible issue board for the beta, ordered by user harm, document integrity, security, and release impact. Every deferred defect needs an owner and rationale.
